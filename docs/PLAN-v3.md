## 2. 온톨로지 정직 평가 — "라벨 그래프까지 왔고, 온톨로지는 아직"

실측(2026-07-24):

```
node types: topic 11 · person 36 · tool 39 · app 37   (계 123)
edge types: interested 71 · belongs 76 · made 38 · uses 50   (계 235)
edges have provenance?: False
nodes have provenance?: False
```

잘된 것: 노드 4유형·엣지 4관계, 참조 무결성·고립 0, 주제 클러스터 시각화.
PRD의 "경량 그래프(D1 nodes/edges)" 수준에는 도달.

부족한 것 3가지 (PRD 7장 기준):

1. **레시피 차원 부재** — PRD 온톨로지의 핵심은 `앱 = 엔티티(재료) × 패턴(조리법)`.
   현재 그래프에는 엔티티·패턴 노드가 없어 "무엇으로 만들었나"(uses)는 답해도
   "어떤 구조인가"는 못 답한다. 예: 차량운행일지 = 엔티티(차량·운행기록·이용자) ×
   패턴(사진→AI인식·예약·통계 대시보드). 이게 있어야 "출결 QR 앱과 재물관리 앱이
   같은 패턴을 공유" 같은 온톨로지다운 연결이 나온다.
2. **근거(provenance) 부재** — 관계에 `evidence: [message_ids]`가 없어
   관계 클릭 → 원문 검증이 불가. PRD 위키 v2의 출처 원칙과 어긋남.
3. **질의 불가** — 그래프가 JS 배열이라 다단계 질의("파이어베이스 쓰는 앱을 만든
   사람들의 공통 관심 주제는?") 수단이 없음.

## 3. Neo4j 판단 — 적용 안 되어 있고, 지금은 넣지 않는다

- 현재 코드 어디에도 Neo4j/TypeDB 없음.
- 123노드·235엣지는 Neo4j가 풀 문제 규모가 아님. PRD 자체도 Neo4j를 버리고
  "경량 그래프 + 결정적 매칭"을 선택했고 그 판단이 옳음.
- 다단계 질의는 이 규모에선 클라이언트 메모리 BFS(2~3홉)로 충분.
- 다만 데이터 모델을 트리플 `(source, relation, target, evidence[], weight)`로
  정규화해 두면 나중에 Neo4j AuraDB(무료 티어)로 내보내기 한 줄이면 됨.
  → **"Neo4j-ready, Neo4j-later"** 전략.

## 4. 아키텍처 (유료 Blaze 반영)

```
[공개] Hosting          앱 껍데기 + 로그인 + 관리자 페이지 (민감 데이터 없음)
[인증] Auth             Google 로그인 + Custom Claims(admin/user)
[원천] Firestore        messages · threads · digests · graph(트리플+근거) · config
[서버] Cloud Functions  제외 캐스케이드 · claims 부여 · 집계 사전계산
[보호] 보안 규칙        멤버만 읽기 · hidden 전송차단 · admin만 쓰기
[이미지] Storage        인증 로드(getBlob) · 숨김 동일 적용
```

### Cloud Functions 3용도 (유료로 해금된 정공법)
1. **제외 캐스케이드 서버 처리** — 관리자가 "이 사람 제외" 토글 → Function이
   메시지 hidden·그래프 노드·집계를 일괄 갱신. (브라우저 처리의 반쪽-상태 위험 제거)
2. **Custom Claims 등급 관리** — allowlist를 규칙에 하드코딩하지 않음.
   관리자 페이지에서 멤버 추가 → Function이 claim 부여. 규칙 재배포 불필요.
3. **집계 문서 사전 계산** — 통계·참여자 카운트를 서버 유지 → 초기 로드 경량화.

### 데이터 모델 (Firestore)
- `messages/{id}` — 본문·작성자·시각·kind·이미지 참조 + `hidden` 플래그
- `threads/{id}` — 주제 스레드(제목·요약·카테고리·message_ids)
- `digests/{categoryId}` — 요지 산문(관리자 편집 가능) + 파생 캐시
- `graph/{tripleId}` — `(source, relation, target, evidence[], weight)` 트리플
- `config/members` — 이메일·등급 / `config/exclusions` — 제외 인물·키워드
- `aggregates/*` — 서버 계산 통계

### 진짜 제외가 보장되는 이유
- hidden 문서는 보안 규칙이 **전송 자체를 차단** → devtools로도 안 보임.
- 파생 뷰(통계·참여자·링크·그래프)는 hidden 아닌 데이터로만 서버 재계산.
- 예외: 요지 산문은 사람이 쓴 글이라 제외 인물 이름이 남을 수 있음
  → 관리자 페이지의 요지 편집 UI로 수정.

## 8. 자동 수집 (P5) — Codex Computer Use

사용자 결정: **ChatGPT Codex의 Computer Use**로 카톡을 자동 갱신한다.

### 전제 — 카카오톡은 대화 읽기 API가 없다
오픈빌더·비즈메시지는 봇이 받은 메시지만 다루며, 단톡방 전체 대화를 읽는 공식 경로는
없다. 따라서 UI 자동화가 유일한 실질 경로다.

### Computer Use의 역할을 최소화한다 (핵심 설계 판단)
- ✗ **화면에서 대화를 읽어오는 방식** — 카톡은 가상 스크롤이라 긴 대화 누락·중복이
  쉽고, 화면 텍스트만 잡혀 줄바꿈·장문이 잘린다. 매일 수백 건이면 오차 누적.
- ✅ **"대화 내용 저장" 클릭까지만 Computer Use** — 대화방 열기 → 메뉴 →
  대화 내용 저장 → 저장 확인, 4~5스텝. 이후 파싱은 검증된 기존 코드가 처리.
  깨질 표면이 최소이고 원본 txt이므로 데이터 정확도 100%.

### 파이프라인
```
[Codex Computer Use]  카톡 열기 → 대화 내용 저장 → txt 생성            (UI 4~5스텝)
        ↓ 새 txt 감지
[결정론적 코드]        파싱 → 마지막 timestamp 이후만 증분 추출
                      → messages/participants 갱신 → 빌드 → 테스트     (LLM 불필요)
        ↓ 새 메시지 N건 이상 누적 시
[LLM 1회 호출]         주제 스레드 분류 + 요지 산문 갱신               (실패해도 폴백)
```

**LLM은 파이프라인 실행에 쓰지 않는다.** 파싱·증분 병합·빌드는 결정론적 코드가 더
정확·저렴·안정적이다. LLM이 필요한 곳은 주제 분류와 요지 산문뿐이며, 이를 분리하면
매일 돌려도 비용이 거의 없고 LLM 실패가 파이프라인을 망치지 않는다.

### 새로 만들어야 할 것 (현재 없음)
1. **증분 추출** — `messages.jsonl`의 마지막 timestamp 기준으로 새 메시지만 분리
   (2026-07-24 반영은 수동 판단으로 처리했음)
2. **중복 처리 방지** — 처리한 txt의 SHA-256 기록, 같은 파일 재처리 시 무해
3. **미분류 폴백 스레드** — 주제 커버리지 100%가 테스트 조건이므로, LLM 분류 실패 시
   "미분류" 임시 스레드에 넣고 나중에 정리
4. (P1 이후) **Firestore 적재** — 파일 갱신 대신 Firestore 문서 업서트

### 유의
- PC가 켜져 있어야 하고, 카톡 UI 변경 시 4~5스텝 셀렉터 점검 필요
- 대화 내보내기는 방장/참여자 권한 내 정상 기능이지만, **멤버 동의 전제는 그대로**
