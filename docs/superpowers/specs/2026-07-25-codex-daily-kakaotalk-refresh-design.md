# Codex 예약 기반 카카오톡 아카이브 일일 갱신 설계

## 목적

Codex 앱의 `예약됨` 기능을 사용해 매일 오전 4시(Asia/Seoul)에
`바이브코딩,업무자동화 화상회의모임` 카카오톡 대화를 수집하고, 아카이브의
대화·사진·통계·주제 문서·지식 그래프를 갱신한 뒤 Firebase에 배포한다.

별도 OpenAI API 호출 코드를 운영하지 않는다. 새 메시지의 의미 분석은 예약
작업으로 실행되는 Codex가 담당한다. 수집이나 검증이 실패하면 원격 데이터를
변경하지 않아 직전 정상 공개본을 유지한다.

## 운영 전제

- 예약 작업은 Codex에 등록된 로컬 프로젝트 `카톡데이터크롤링`
  (`D:\apps\카톡데이터크롤링`)에서 독립형 로컬 작업으로 실행한다.
- 실행 시각은 매일 오전 4시, 시간대는 `Asia/Seoul`이다.
- Windows PC와 Codex 앱이 실행 중이어야 한다.
- Windows 세션은 잠금 해제 상태이고 PC 카카오톡은 로그인되어 있어야 한다.
- 대상 채팅방은 PC 카카오톡에서 접근 가능한 상태여야 한다.
- Firebase 서비스 계정과 기존 프로젝트 설정은 현재 로컬 구성을 사용한다.
- 카카오톡 내부 데이터베이스나 캐시는 읽지 않고 공식 PC 화면과 대화 내보내기
  기능만 사용한다.

## 수집 범위

매일 다음 항목을 함께 갱신한다.

- 사람이 작성한 메시지의 날짜, 시간, 닉네임, 여러 줄 본문
- 본문에 포함된 URL
- `파일: 파일명` 형태의 첨부파일 공유 기록
- 채팅방에서 다운로드할 수 있는 사진 원본
- 사진의 메시지 시각, 닉네임, 같은 시각 내 순서
- 참여자 및 월별 활동 통계
- 기존 12개 주제 체계에 따른 대화 스레드
- 주제별 요약 문서
- 사람·도구·프로젝트·주제를 연결하는 지식 그래프

기존 수집 정책을 유지해 동영상, 이모티콘, 입퇴장·초대 등의 시스템 메시지는
제외한다. 첨부 문서의 바이너리는 내려받지 않고 파일명 기록만 보존한다.

## 아키텍처

### 1. Codex 예약 오케스트레이터

Codex의 독립형 cron 예약 작업이 전체 갱신을 지휘한다. 장기 대화에 실행 결과를
누적하는 heartbeat가 아니라 매일 별도 로컬 작업으로 실행해 각 실행의 성공과
실패를 독립적으로 확인할 수 있게 한다.

예약 작업은 저장소의 운영 지침과 실행 스크립트를 읽고 아래 단계를 순서대로
수행한다. 동일 날짜에 다시 실행해도 같은 입력으로 중복 메시지나 중복 사진을
만들지 않아야 한다.

### 2. 카카오톡 화면 수집기

Computer Use로 PC 카카오톡에서 대상 채팅방을 열고 대화를 TXT로 내보낸다.
새로 저장한 원본은 이전 정상 원본과 구분되는 준비 영역에 놓고, 파일 존재 여부,
방 이름, 마지막 메시지 시각, 파일 크기를 먼저 확인한다.

사진은 채팅방 서랍에서 새 사진만 다운로드한다. 기존 해시와 같은 파일은 다시
보관하지 않는다. 메시지와 확실히 연결되는 사진만 `assets/images/YYYY-MM/`에
등록하고, 연결 근거가 부족한 파일은 `assets/staging/`에 두어
`needs_review` 또는 `unresolved`로 기록한다. 불확실한 사진을 임의 연결하지
않는다.

### 3. 구조화 및 증분 분석

기존 파서로 전체 TXT를 다시 구조화해 안정적인 메시지 ID와 이미지 메시지 ID를
생성한다. 이전 데이터와 비교해 새 메시지 구간을 식별하되, 최종 산출물은 전체
대화를 기준으로 검증한다.

Codex는 새 메시지를 기존 12개 주제에 우선 배치하고 자연스러운 대화 묶음으로
스레드를 추가하거나 기존 최신 스레드를 연장한다. 기존 주제로 설명할 수 없는
내용이 반복적으로 나타날 때만 새 주제를 추가한다. 이어서 영향받은 주제 요약과
지식 그래프를 갱신한다. 기존 과거 메시지의 분류는 명백한 오류가 아닌 한
불필요하게 변경하지 않는다.

### 4. 검증 및 발행

구조화·분석 후 다음 검증을 모두 통과해야 발행한다.

- 파서, 이미지 연결, 사이트 조립, Firestore 페이로드 테스트 통과
- 메시지 ID, 이미지 ID, 이미지 자산 ID의 중복 없음
- 새 원본의 마지막 정상 메시지가 기존 원본보다 이전으로 후퇴하지 않음
- 모든 공개 메시지가 정확히 하나의 주제 스레드에 포함됨
- 주제 요약과 지식 그래프가 존재하는 메시지·주제·인물만 참조함
- 다운로드 완료로 표시한 사진이 실제로 존재하고 크기와 SHA-256이 일치함
- 제외 규칙 적용 후 통계와 파생 데이터의 합계가 일치함
- Firebase 업로드 전 페이로드 dry-run 성공

검증이 통과하면 Firestore 페이로드를 만들고, Firestore와 Storage를 동기화한 뒤
Firebase Hosting을 배포한다. 정적 셸이 바뀌지 않았더라도 일관된 운영 절차를
위해 Hosting 배포까지 수행한다.

## 데이터 흐름

1. Codex 예약 작업이 매일 오전 4시에 로컬 프로젝트에서 시작된다.
2. 카카오톡 PC에서 전체 대화 TXT와 새 사진을 준비 영역에 수집한다.
3. 수집 결과를 검증하고 기존 정상 원본보다 최신인지 확인한다.
4. `messages.jsonl`, `images.jsonl`, `participants.json`을 원자적으로 갱신한다.
5. 새 메시지에 맞춰 `topics.json`, `topic-digests.json`,
   `knowledge.json`을 갱신한다.
6. 전체 테스트와 교차 검증을 실행한다.
7. Firestore 페이로드 dry-run을 실행한다.
8. 성공한 경우에만 Firestore·Storage 업로드와 Firebase Hosting 배포를
   수행한다.
9. 실행 결과에 수집·분석·업로드 건수와 공개 URL을 남긴다.

## 실패 처리와 복구

- 카카오톡 창, 대상 채팅방 또는 내보내기 메뉴를 찾지 못하면 수집 실패로
  종료하고 배포하지 않는다.
- 내보낸 TXT가 비어 있거나 기존 정상본보다 과거 상태면 기존 데이터를 유지한다.
- 사진 다운로드 일부가 실패해도 텍스트 갱신은 가능하지만, 실패 사진은
  `pending`, `unavailable` 또는 `needs_review`로 명시해야 한다.
- 주제 커버리지나 지식 그래프 참조 무결성이 깨지면 배포하지 않는다.
- Firestore·Storage 업로드 도중 실패하면 Hosting 배포를 진행하지 않고 실패
  단계를 보고한다. 다음 실행은 멱등 동기화로 같은 자료를 다시 올릴 수 있다.
- Firebase 업로드 전 로컬 산출물은 이전 정상 산출물의 복구 사본을 유지한다.
- 예약 작업은 성공과 실패 모두 요약을 남기며, 실패 시 사람이 바로 확인할 수
  있도록 알림을 유지한다.

## 보안과 개인정보

- `serviceAccountKey.json`, 멤버 이메일, 카카오톡 원본, 사진은 Git에
  커밋하지 않는다.
- 공개 Hosting 번들에는 대화나 이미지 원본을 포함하지 않는다.
- 대화는 기존 Google 로그인과 Firestore·Storage 규칙을 통과한 등록 멤버에게만
  제공한다.
- 서비스 계정 키와 인증 토큰을 예약 작업 출력에 표시하지 않는다.
- 새 참여자가 생겨도 멤버 허용 목록은 자동으로 확대하지 않는다.

## 테스트 전략

### 자동 테스트

- 기존 단위 테스트 전체 실행
- 같은 원본을 두 번 처리하는 멱등성 테스트
- 기존 원본에 새 날짜 메시지를 추가한 증분 갱신 테스트
- 사진 중복 해시와 불확실 연결 처리 테스트
- 신규 메시지의 주제 커버리지와 요약 합계 테스트
- 손상되거나 과거로 후퇴한 TXT에서 발행이 차단되는 테스트
- Firebase 업로드 명령의 dry-run 테스트

### 최초 운영 검증

예약을 활성화하기 전에 낮 시간에 한 번 수동으로 전체 작업을 실행한다.
카카오톡 내보내기, 새 사진 연결, AI 분류, Firestore 반영, 로그인 후 페이지
표시를 확인한다. 이 시험 실행이 성공한 뒤 오전 4시 예약을 활성화한다.

## 완료 기준

- Codex `예약됨` 목록에 매일 오전 4시 실행되는 활성 독립형 작업이 보인다.
- 새 메시지와 다운로드 가능한 새 사진이 다음 정상 실행 후 페이지에 나타난다.
- 통계, 주제 문서, 스레드, 지식 그래프도 같은 실행에서 갱신된다.
- 실패한 실행은 기존 공개 페이지를 손상시키지 않고 원인과 중단 단계를 남긴다.
- 같은 입력으로 재실행해도 메시지, 사진, Firestore 문서가 중복되지 않는다.
