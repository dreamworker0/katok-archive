# 따뜻한 커뮤니티 아카이브 UI 개편 디자인

- 작성일: 2026-07-26
- 상태: 사용자 승인 완료
- 대상: 로그인, 승인 대기, 아카이브 전체 화면, 내 글 관리, 관리자 화면
- 우선 환경: PC, 모바일 반응형 지원

## 1. 목표

현재 아카이브의 기능과 보안 구조는 유지하면서 화면의 인상을 “관리 도구”에서
“사람들의 대화와 활동을 편안하게 다시 만나는 공동 기록 공간”으로 바꾼다.

성공한 화면은 다음 느낌을 준다.

1. 첫 화면에서 기능 목록보다 사람과 기록이 먼저 보인다.
2. 긴 대화와 보고서를 읽을 때 화면이 빽빽하거나 피곤하지 않다.
3. 로그인부터 관리자 작업까지 같은 서비스 안에 있다는 인상이 유지된다.
4. 따뜻한 분위기 때문에 삭제·탈퇴 같은 위험한 작업의 의미가 흐려지지 않는다.
5. PC에서는 모든 기능을 쉽게 찾고, 모바일에서는 자주 쓰는 기능에 빠르게 접근한다.

## 2. 변경하지 않는 것

이번 작업은 UI 개편이다. 다음 동작과 데이터 경계는 유지한다.

- Firebase Auth, Firestore, Storage, Cloud Functions 구조
- 멤버·관리자 권한과 보안 규칙
- `data-view` 기반 화면 전환과 기존 8개 화면
- 검색, 참여자 필터, 테마 전환
- 주제별 지식, 관계망, 타임라인, 갤러리, 첨부파일, 통계
- 내 글 관리의 수집 동의와 삭제 요청
- 관리자 승인, 반려, 역할 변경, 탈퇴, 주제 발행 제외
- 로컬 `site/` 미리보기와 Firebase Hosting 빌드 경로

데이터 스키마, 수집 파이프라인, 업로드 방식은 변경하지 않는다.

## 3. 디자인 방향

디자인 이름은 **따뜻한 아카이브**다.

### 3.1 색상

| 역할 | 색상 | 용도 |
|---|---|---|
| 종이빛 배경 | `#FBF6EE` | 앱 기본 배경 |
| 카드 표면 | `#FFFDF8` | 카드·입력·패널 |
| 먹빛 | `#3C332C` | 제목과 핵심 본문 |
| 살구빛 | `#CA7154` | 주 행동, 선택, 환영 |
| 세이지 | `#879D78` | 지식, 완료, 안정 상태 |
| 옅은 살구 | `#F4DDCF` | 환영 영역과 새 기록 |
| 위험색 | `#B85F4B` | 삭제, 탈퇴, 수집 중단 |

색만으로 상태를 전달하지 않는다. 아이콘·라벨·설명을 함께 쓴다.

### 3.2 어두운 테마

현재 테마 전환 기능을 유지한다. 어두운 테마는 검정보다 따뜻한 갈색을 사용한다.

- 배경: `#292521`
- 표면: `#37312C`
- 본문: `#F4EBDD`
- 보조 본문: `#CABBAC`
- 살구 강조: `#DF8B6D`
- 세이지 강조: `#9CAE8C`

일러스트는 별도 이미지를 만들지 않고 투명도와 주변 표면색으로 두 테마에 대응한다.

### 3.3 타이포그래피

- 한국어 시스템 글꼴 스택을 사용해 외부 폰트 다운로드에 의존하지 않는다.
- 제목: 700~800 굵기, 좁은 자간
- 본문: 400~500 굵기, `1.7~1.85` 줄 간격
- 긴 글의 최대 읽기 폭: 약 68~72자
- 메타 정보와 보조 설명은 작게 하되 최소 가독 크기를 지킨다.
- 영문 대문자 장식은 짧은 섹션 라벨에만 쓴다.

### 3.4 형태와 움직임

- 카드 모서리: 14~20px
- 버튼과 입력 모서리: 10~12px
- 그림자는 낮고 넓게 사용한다.
- 모든 영역을 카드로 감싸지 않는다. 의미가 다른 덩어리만 표면으로 구분한다.
- 화면 전환은 160~220ms의 짧은 페이드와 이동만 허용한다.
- `prefers-reduced-motion`에서는 장식 움직임을 제거한다.

## 4. 정보 구조

### 4.1 PC

기존 상단의 긴 탭 행을 왼쪽 사이드바로 옮긴다.

```text
우리의 기록

둘러보기
  주제별 지식
  타임라인
  관계망

모아보기
  갤러리
  첨부파일
  통계

나의 공간
  내 글 관리
  관리자

현재 사용자 / 테마 / 로그아웃
```

- 사이드바 폭은 약 232~248px로 고정한다.
- 관리자 항목은 기존처럼 관리자에게만 보인다.
- 검색과 참여자 필터는 콘텐츠 상단의 고정 유틸리티 바에 둔다.
- 본문은 화면 전체로 늘리지 않고 최대 폭을 제한한다.
- 1280px 이상에서는 카드 2~3열, 1024px 부근에서는 2열을 기본으로 한다.

### 4.2 모바일

모바일에서는 사이드바를 없애고 하단 내비게이션을 사용한다.

- 홈
- 타임라인
- 사진
- 내 기록
- 더보기

`더보기`에는 관계망, 첨부파일, 통계, 관리자, 테마, 로그아웃을 둔다.
검색은 상단에 유지하고 참여자 필터는 검색 옆의 필터 버튼에서 연다.

### 4.3 브랜드 표현

화면의 대표 이름은 **우리의 기록**으로 한다. 기존 채팅방 이름과
“사회복지 바이브코딩 아카이브”는 부제 또는 메타 정보로 보존한다.

## 5. 주요 화면

### 5.1 로그인

PC에서는 대표 일러스트와 로그인 카드를 나란히 배치한다. 모바일에서는 일러스트를
위로 줄여 세로 배치한다.

- 제목: “함께 만든 기록을 다시 만나는 곳”
- Google 로그인 버튼은 한 개의 명확한 주 행동으로 표시한다.
- 회원 전용이라는 사실과 로그인 정보의 용도를 버튼 아래에 짧게 설명한다.
- 인증 오류는 기술 코드보다 사용자가 다음에 할 행동을 먼저 보여준다.

### 5.2 열람 신청과 승인 대기

- 신청 화면은 입력 하나와 제출 행동에 집중한다.
- 참여자 명단은 기존 보안 정책대로 노출하지 않는다.
- 승인 대기는 “신청 완료 → 관리자 확인 → 열람 가능”의 세 단계로 보여준다.
- 다시 확인, 이름 수정, 다른 계정 사용은 보조 행동으로 둔다.
- 승인 대기용 작은 일러스트를 사용해 막힌 오류 화면처럼 보이지 않게 한다.

### 5.3 주제별 지식 홈

첫 화면은 기능 설명보다 현재 기록의 상태를 보여준다.

- 이번 달 또는 최근 갱신 안내
- 최근 이어진 이야기
- 사람과 지식의 연결
- 새 사진과 첨부
- 관계망으로 가는 짧은 진입점

기존 주제별 지식 데이터에서 계산 가능한 내용만 표시한다. 새로운 서버 집계는 만들지
않는다.

### 5.4 타임라인과 긴 글

- 본문 폭을 제한하고 메시지 사이의 리듬을 넓힌다.
- 날짜 구분선은 강한 선보다 여백과 작은 라벨로 표시한다.
- 작성자, 시각, 종류는 본문보다 한 단계 낮춘다.
- 검색 결과와 선택된 참여자는 상단에 지울 수 있는 필터 칩으로 보여준다.
- 사진과 첨부는 본문 흐름 안에 자연스럽게 배치한다.

### 5.5 갤러리·첨부·통계·관계망

- 갤러리는 사진을 주인공으로 두고 장식 이미지를 사용하지 않는다.
- 첨부파일은 파일명, 종류, 공유 시점, 관련 주제를 우선 표시한다.
- 통계는 숫자 카드 수를 줄이고 의미 있는 비교와 설명을 함께 제공한다.
- 관계망은 그래프 영역을 넓게 유지하고 검색·범례·선택 정보만 따뜻한 카드 스타일로
  통일한다.

### 5.6 내 글 관리

내 글 관리의 핵심은 사용자의 통제권이다.

- `public`, `unpublished`, `none` 대신 화면에서는
  “함께 공개”, “발행하지 않기”, “수집 중단”을 사용한다.
- 각 선택이 수집과 발행에 어떤 영향을 주는지 바로 설명한다.
- “발행하지 않기”는 수집은 계속되지만 일반 멤버 화면에서는 제외되고 운영상 원본은
  관리자에게 남는다는 사실을 숨기지 않는다.
- 글·사진·첨부는 현재처럼 구분하고 선택 가능한 목록으로 제공한다.
- 되돌릴 수 없는 작업은 결과 설명 → 재확인 → 실행의 세 단계로 처리한다.
- 서버에 전달하는 실제 값은 기존 값을 유지한다.

### 5.7 관리자

관리자 첫 영역에는 처리할 일의 수를 보여준다.

- 승인 대기
- 현재 멤버
- 반영할 요청
- 발행에서 제외한 주제

승인·반려처럼 자주 쓰는 행동과 역할 변경·탈퇴처럼 위험한 행동을 시각적으로 분리한다.
표시명 연결은 드롭다운과 선택 칩을 유지하되 선택 결과를 더 명확하게 보여준다.

## 6. 이미지 생성 계획

이미지는 장식이 아니라 서비스의 정체성과 상태 설명에 사용한다.

### 6.1 대표 이미지

- 용도: 로그인과 주제별 지식 홈
- 비율: 8:5 가로형, 중요한 요소는 중앙 70% 안에 배치
- 스타일: 종이를 오려 붙인 듯한 부드러운 편집 일러스트
- 소재: 겹쳐진 기록지, 말풍선, 햇빛, 잎사귀, 이어지는 선
- 색상: 아이보리, 살구, 세이지, 옅은 황토
- 금지: 식별 가능한 얼굴, 실제 카카오톡 UI, 로고, 문자, 워터마크

### 6.2 상태 이미지

다음 세 장을 같은 스타일로 생성한다.

1. 승인 대기: 봉투와 차곡차곡 쌓인 기록지
2. 빈 기록: 열린 기록함과 작은 새싹
3. 검색 결과 없음: 돋보기와 흩어진 말풍선

상태 이미지는 메시지보다 작게 사용하며 오류 설명을 대체하지 않는다.

### 6.3 파일과 성능

- 대표 이미지: WebP, 목표 250KB 이하
- 상태 이미지: 투명 WebP 또는 PNG, 각 80KB 이하
- 원본 생성물과 웹 최적화본을 분리한다.
- 첫 화면 대표 이미지만 우선 로드하고 나머지는 지연 로드한다.
- 모든 이미지에 의미 있는 대체 텍스트를 제공한다.

## 7. 구현 경계

### 7.1 HTML

`web/index.html`의 앱 껍데기를 사이드바, 유틸리티 바, 콘텐츠 마운트로 재구성한다.
기존 JavaScript가 찾는 ID와 `data-view` 값은 유지한다.

Firebase Hosting용 `web/index.hosting.html`도 동일한 구조를 사용해야 한다.
두 파일의 차이는 현재처럼 Firebase 로딩과 인증 부트스트랩에만 둔다.

### 7.2 CSS

`web/styles.css` 상단에 디자인 토큰을 CSS 변수로 정의한다.

- 색상
- 간격
- 모서리
- 그림자
- 본문 폭
- 사이드바 폭
- 전환 시간

기존 화면별 스타일은 새 공용 컴포넌트 스타일 아래로 점진적으로 정리한다.
데이터 렌더링 로직과 무관한 시각 규칙은 JavaScript 문자열 안에 넣지 않는다.

### 7.3 JavaScript

기존 렌더러와 Firebase 데이터 흐름을 유지한다. 필요한 동작 변경은 다음으로 제한한다.

- 데스크톱 사이드바와 모바일 하단 내비게이션의 활성 상태 동기화
- 모바일 `더보기` 패널
- 필터 칩 표시와 해제
- 위험 행동 확인 패널
- 로그인·대기·오류 상태에 새 클래스 적용

기존 `setView()`와 `data-view` 계약을 유지해 화면별 렌더러를 다시 작성하지 않는다.

## 8. 오류와 빈 상태

모든 오류는 세 부분으로 구성한다.

1. 무슨 일이 일어났는지
2. 데이터가 안전한지 또는 작업이 반영되지 않았는지
3. 사용자가 다음에 할 수 있는 일

예:

- 로그인 취소: 다시 로그인
- 권한 없음: 열람 신청 또는 다른 계정 사용
- 데이터 로드 실패: 다시 시도, 계속 실패하면 관리자에게 알릴 정보
- 검색 결과 없음: 필터 해제
- 이미지 실패: 대체 정보와 다시 불러오기

오류 상태에서도 원본 Firebase 오류 메시지는 개발자 진단용으로 보존하되 기본 화면에서는
접어 둔다.

## 9. 접근성

- 키보드만으로 모든 내비게이션과 관리자 작업을 수행할 수 있어야 한다.
- 현재 위치는 색상뿐 아니라 `aria-current`와 형태로 표시한다.
- 포커스 링을 제거하지 않는다.
- 본문과 배경은 WCAG AA 명암 대비를 충족한다.
- 아이콘 버튼에는 접근 가능한 이름을 제공한다.
- 모달과 모바일 더보기 패널은 포커스를 가두고 닫을 때 원래 위치로 돌려보낸다.
- 그래프와 이미지에는 텍스트 대체 경로를 유지한다.

## 10. 검증

### 10.1 자동 검증

기존 테스트를 모두 통과해야 한다.

```powershell
python -m unittest discover -s tests -p "test_*.py"
npm.cmd test
```

추가할 검증:

- 로컬·Hosting HTML에 필수 ID와 `data-view`가 동일하게 존재
- 모든 내비게이션 대상이 기존 렌더러와 연결됨
- 생성 이미지 파일이 빌드 결과에 포함됨
- 이미지 용량 상한 검증

## 11. 완료 조건

- 승인된 따뜻한 아카이브 디자인이 모든 화면에 적용된다.
- PC 사이드바와 모바일 하단 내비게이션이 동일한 화면 상태를 제어한다.
- 로그인·승인 대기·내 글·관리자 화면이 같은 디자인 언어를 사용한다.
- 생성된 대표 이미지와 세 개의 상태 이미지가 최적화되어 적용된다.
- 기존 기능, 데이터 흐름, 권한, 보안 규칙이 바뀌지 않는다.
- 기존 127개 테스트와 새 UI 계약 테스트가 모두 통과한다.
- 지정한 다섯 화면 너비에서 주요 상태를 시각 검증한다.
